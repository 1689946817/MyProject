二、项目背景与设计目标
1. 项目背景
随着图像、文档截图、图表和版面化 PDF 等多模态数据规模增长，传统仅基于文本关键词或低层视觉特征的检索方案难以支撑高质量问答与知识服务。传统 RAG 方案虽然能提升纯文本问答效果，但面对图像、表格、页面截图等视觉信息时，常出现知识缺口、上下文不足和回答不可靠的问题。

当前课题提出的核心思路不是直接依赖复杂的跨模态统一向量空间，而是利用多模态大模型的图像理解能力，将图像或文档中的视觉内容转写为结构化文本描述，再复用成熟的文本嵌入、向量检索和生成增强问答链路。这种“语义描述桥接”设计兼顾了系统可解释性、轻量性、工程实现难度和后续扩展性。

2. 设计目标
本系统面向“多模态知识入库、统一检索、会话问答和实验评测”四类需求，设计目标如下：
（1）实现图片知识库和文档知识库的统一管理，支持上传、解析、元数据维护和状态跟踪。
（2）实现文本到图像、图像到图像的双路检索能力，并支持文档片段与页面图像的统一召回。
（3）实现基于检索增强生成的多模态智能问答，支持会话历史、引用来源和检索过程追踪。
（4）构建可扩展的分层架构，使图像理解模型、嵌入模型、向量库和前端展示层能够松耦合集成。
（5）提供离线评测能力，支持 Proposed 方法与多种 Baseline 方法在公开数据集上的可重复对比实验。

三、系统总体设计
1. 总体架构
结合开题报告中的原始设想和当前仓库实现，系统总体采用五层架构：

（1）数据层
负责原始图片、PDF 文档、页面渲染图、表格裁剪图、业务元数据和会话消息的统一存储。当前系统使用本地文件存储保存原始资源，使用 SQLite 保存元数据和会话数据，使用 ChromaDB 保存向量索引，并辅以 BM25 索引支持混合检索。

（2）语义化层
负责将原始图像或文档中的视觉内容转化为可检索、可生成的文本表达。对图片，主要通过多模态大模型生成结构化描述；对 PDF 文档，主要通过文本抽取、页面解析、视觉资产提取和必要的图像描述补全，形成文本块与图像资产共同组成的知识单元。

（3）检索层
负责对描述文本、文档片段和用户查询进行统一向量化和近邻搜索，并在需要时结合 BM25 和重排序策略，提高召回质量和结果稳定性。该层还负责图片集合、文档集合和元数据过滤条件的组织。

（4）应用层
负责双路检索调度、RAG 问答编排、会话持久化、引用溯源和任务流程控制。文本输入直接进入文本检索链路；图片输入先生成语义描述，再进入统一检索链路。应用层还负责生成最终回答并记录当轮检索参数和来源快照。

（5）展示层
负责面向用户提供统一 Web 交互入口。当前前端已形成四个主要页面：图片知识库、文档知识库、检索页和聊天页，支持结果可视化、管理操作、引用图片展示和会话历史浏览。

2. 核心设计思想
（1）统一文本语义中间层。无论知识源来自图片还是文档，最终都尽量归一为结构化文本与元数据，使系统能复用成熟的文本检索链路。
（2）检索与生成解耦。检索层负责召回与排序，生成层只消费检索结果，降低系统耦合度。
（3）多存储协同。关系型数据库负责业务元数据，向量库存放语义索引，文件系统保存原始资源，三者以统一 ID 和文件路径建立映射。
（4）可解释优先。聊天回答不仅返回答案，还返回来源、相似度、检索步骤和上下文痕迹，支撑系统可信性与论文展示。
（5）面向实验演进。系统除在线业务流程外，还保留独立评测模块，支持不同检索方案的离线比较。

3. 总体业务流程
（1）知识入库：用户上传图片或 PDF，系统生成描述或解析片段，写入关系库、文件存储和向量库。
（2）统一检索：用户输入文本或图片，系统将查询统一转化为文本语义表示，再执行检索和排序。
（3）RAG 问答：系统结合会话历史、检索结果和用户问题构建上下文，由大语言模型生成回答。
（4）结果回溯：前端根据返回的来源和元数据展示原图、文档片段、页面号和相似度。
（5）实验评测：评测脚本加载数据集，调用不同方法进行检索或生成，并输出 Recall、MRR、mAP 等指标。

四、功能设计
1. 图片知识库功能设计
图片知识库模块面向图片数据的采集、语义化处理和管理，主要功能包括：
（1）多图片上传。支持用户一次上传一张或多张图片。
（2）自动描述生成。上传完成后，系统调用多模态模型为图片生成结构化描述。
（3）图片元数据管理。支持维护标题、来源数据集、标签、备注、是否启用等字段。
（4）状态跟踪。对每条图片记录维护 Processing、Completed、Failed 等处理状态。
（5）列表筛选与检索。支持按关键字、标签、来源、状态和启用状态筛选图片。
（6）重处理。对已有图片重新触发语义描述生成与向量同步。
（7）删除。删除图片记录时同步清理相关向量索引和文件资源引用。

2. 文档知识库功能设计
文档知识库用于管理 PDF 等文档型知识源，主要功能包括：
（1）PDF 上传。前端限制上传 PDF 文件，后台为每份文档创建独立记录。
（2）后台解析。系统异步执行文本抽取、页面图像提取、表格页渲染和片段切分。
（3）解析进度跟踪。记录 parse_stage、progress_percent 和 progress_message，前端可轮询查看。
（4）结果查看。用户可查看文档解析得到的文本片段和关联图片资产。
（5）文档元数据管理。支持标题、标签、备注、文档类型、启用状态、自定义元数据维护。
（6）重处理。支持重新加入文档解析队列。
（7）删除。删除文档时同步清理文档向量、关联图片资产和元数据记录。

3. 双路检索功能设计
系统检索模块面向文本与图像两类查询输入，主要功能包括：
（1）文本到图像检索。用户输入自然语言查询，系统直接执行文本向量检索，返回相关图片或页面图像。
（2）图像到图像检索。用户上传查询图片，系统先生成文本描述，再执行统一文本检索。
（3）结果评分与排序。检索结果返回相似度分数，必要时结合重排序模块优化结果。
（4）结果标签展示。检索结果可携带 asset_type、page_number、table_group_id 等元数据，用于前端展示页面图、表格裁剪图和跨页延续信息。
（5）多知识源扩展。当前架构已支持图片知识库和文档知识库中的视觉资产统一参与检索。

4. 多模态 RAG 问答功能设计
聊天与问答模块是系统的核心服务能力，主要功能包括：
（1）单轮或多轮问答。用户可以直接提问，也可在已有 session 中持续对话。
（2）支持文本问题与图片附件。若问题附带图片，则先进行语义化处理，再参与检索与回答生成。
（3）检索增强生成。系统先检索相关图片描述或文档片段，再将其作为上下文交给生成模型。
（4）回答来源展示。返回 sources 列表，包含来源类型、来源 ID、标题、文件路径、内容摘要和相似度等字段。
（5）过程追踪。返回 retrieval_steps，辅助展示检索链路和调度决策。
（6）流式响应。系统提供普通问答接口和 SSE 流式接口，提升交互体验。
（7）智能呈现。根据当前实现，聊天消息支持在文本前后展示关联图片，并可突出图像优先模式。

5. 会话管理功能设计
在开题阶段，会话与历史管理通常可视为增强设计；结合当前实现，系统正式纳入以下会话功能：
（1）新建会话。
（2）会话列表查看。
（3）会话详情查看。
（4）会话重命名。
（5）会话删除。
（6）消息持久化，包括用户消息、助手消息、是否含图像、来源快照、检索参数和检索步骤。
（7）按最近若干轮消息构造上下文记忆，参与后续对话。

6. 离线评测功能设计
为支撑论文实验，系统单独设计 evaluation 模块，主要功能包括：
（1）加载 COCO 子集和 UniDoc 子集等评测数据集。
（2）实现 proposed_multimodal_rag、baseline_text_rag、baseline_clip_retrieval、ocr_text_rag 等方法。
（3）计算 Recall@K、MRR、mAP 等指标。
（4）生成评测 JSON 报告，支撑后续论文图表和实验分析。

五、模块设计
1. 后端模块设计
后端采用 FastAPI 组织，主要分为以下子模块：

（1）API 路由模块
位于 backend/app/api/routers 下，负责 HTTP 接口暴露和请求响应封装。
1）kb.py：图片知识库管理接口。
2）docs.py：文档知识库接口。
3）search.py：文本检索和图搜图接口。
4）chat.py：会话管理、普通聊天和流式聊天接口。
5）admin.py：预留管理端点。

（2）应用服务模块
位于 backend/app/application 下，负责业务编排。
1）knowledge_management.py：知识库记录读写、补列、标签和元数据工具。
2）chat_service.py：会话创建、消息写入、历史读取、JSON 字段编解码和数据库渐进升级逻辑。
3）schemas.py：定义对外请求响应模型。

（3）数据模块
位于 backend/app/data 下，负责关系型数据模型和存储路径管理。
1）models.py：图片记录模型 ImageRecord。
2）doc_models.py：文档记录模型 DocumentRecord。
3）chat_models.py：聊天会话和消息模型 ChatSession、ChatMessage。
4）database.py：SQLAlchemy 引擎、SessionLocal、Base 和依赖注入。
5）storage.py：图片和文档文件路径组织。

（4）LangChain 集成模块
位于 backend/app/langchain_integration 下，是当前实现中的核心编排层。
1）adapters.py：提供 process_image_upload、text_to_image_search、image_to_image_search、rag_chat、文档入库与删除同步等统一接口。
2）chains.py：图像描述链和 RAG 链的封装。
3）retrievers.py：统一检索器构建。
4）vectorstores.py：图片集合和文档集合向量库操作。
5）doc_parser.py：PDF 文本抽取、切块、视觉资产提取。
6）mineru_client.py：外部文档解析后端适配。
7）agentic_rag.py、query_transform.py、context_compression.py：增强型检索与问答策略。

（5）检索与排序模块
位于 backend/app/retrieval 下，负责 rerank 和 hybrid retrieval 逻辑，为文本召回提供增强能力。

（6）配置模块
位于 backend/app/core/config.py，负责数据库路径、Chroma 集合名、外部模型接口、RAG 开关和检索参数配置。

2. 前端模块设计
前端基于 Vue3 + TypeScript + Vite，实现四类主要页面和若干公共组件。

（1）页面层
1）KnowledgeBase.vue：图片知识库上传、筛选、编辑、预览和重处理。
2）DocumentKB.vue：文档上传、进度展示、解析结果查看、编辑和重处理。
3）Search.vue：文本到图像检索和图像到图像检索。
4）Chat.vue：会话列表、消息展示、图片引用展示和对话输入。

（2）组件层
1）UploadZone.vue：统一上传区。
2）ImageCard.vue：图片卡片展示。
3）ImagePreviewModal.vue：图片预览弹窗。
4）SessionList.vue：会话列表交互。

（3）API 封装层
位于 frontend/src/api 下，分别封装 kb、docs、search、chat 等请求。

（4）路由层
frontend/src/router/index.ts 统一配置前端路由，使系统以聊天页作为默认入口。

（5）国际化与样式层
使用 locales 管理中英文文案，使用 UnoCSS 与自定义样式变量实现页面表现。

3. 评测模块设计
evaluation 模块独立于在线服务，便于对检索和 RAG 方案进行离线对比：
（1）datasets：数据集加载。
（2）methods：具体方法实现。
（3）evaluators：生成式评估器。
（4）metrics：指标计算。
（5）run_*.py：实验执行脚本。

六、数据库设计
1. 数据库设计原则
本系统数据库设计遵循以下原则：
（1）关系型数据库保存可管理、可更新、可查询的业务元数据。
（2）向量库保存语义索引，不承担业务主表功能。
（3）文件系统保存原始资源和衍生资源，避免将大文件直接存入关系库。
（4）所有核心资源通过统一 ID 或 doc_id 建立映射关系，确保回溯能力。

2. 逻辑数据库设计
结合当前 ORM 设计，系统的核心关系型实体如下：

（1）ImageRecord 图像记录表
用途：保存图片知识库中的图片元数据和语义描述。
关键字段：
id：主键，UUID 字符串。
file_path：图片在本地存储中的路径。
upload_time：上传时间。
generated_description：多模态模型生成的结构化描述。
status：处理状态。
source_dataset：来源数据集。
title：管理标题。
tags：标签列表的字符串表示。
notes：备注。
enabled：是否启用。
custom_metadata：自定义元数据 JSON。
extra_metadata：页面号、资产类型、跨页关系等额外元数据。

（2）DocumentRecord 文档记录表
用途：保存 PDF 文档及其解析过程元数据。
关键字段：
id：主键。
file_name：原始文件名。
title：展示标题。
file_path：文档存储路径。
upload_time：上传时间。
status：文档处理状态。
chunk_count：文本片段数量。
image_count：从文档提取的图像资产数量。
document_type：文档类型，当前以 pdf 为主。
tags：标签。
notes：备注。
enabled：是否启用。
custom_metadata：自定义元数据。
extra_metadata：扩展 JSON 数据。
parse_backend：解析后端类型。
parse_stage：当前解析阶段。
progress_percent：解析进度百分比。
progress_message：进度提示信息。

（3）ChatSession 会话表
用途：保存聊天会话基本信息。
关键字段：
id：会话主键。
title：会话标题。
created_at：创建时间。
updated_at：最后更新时间。

（4）ChatMessage 消息表
用途：保存每轮对话消息及其上下文快照。
关键字段：
id：自增主键。
session_id：所属会话 ID。
role：user 或 assistant。
content：消息正文。
has_image：是否含图片附件。
sources_json：引用来源快照。
retrieval_params_json：本轮检索参数。
retrieval_steps_json：本轮检索步骤。
created_at：消息创建时间。

3. 检索存储设计
除关系型数据库外，系统还设计了以下检索存储：

（1）Chroma 图片集合
主集合名为 images_main_kb，用于保存图片描述向量。
每条向量记录与 ImageRecord.id 对齐，metadata 中保存 file_path、title、source_dataset、enabled 等信息。

（2）Chroma 文档集合
集合名为 documents_text，用于保存文档切块文本及相关 metadata。
每个 chunk 保存 doc_id、chunk_index、file_path 等字段，支撑文档问答和来源追溯。

（3）评测专用集合
如 images_coco_proposed、images_multimodal_embedding 等集合，用于离线实验，避免与主系统在线知识库混用。

（4）BM25 索引
以本地持久化文件形式保存，用于与向量检索进行混合召回，提高检索覆盖度。

4. 文件存储设计
（1）图片原图存放在 storage/images 或 backend/app/data/storage 统一管理的路径体系下。
（2）文档原文件保存在文档存储目录。
（3）文档解析过程中产生的页面渲染图、表格裁剪图等也以文件方式保存，并通过 extra_metadata 与文档、页面号建立映射。

5. 现状数据库实现参考
根据用户指定的 backend/test_data/app_test.db，当前参考库中已存在以下表：
（1）image_records
（2）document_records
（3）chat_sessions
（4）chat_messages

其中，当前参考库体现出“在基础表结构上逐步补列”的演进特征：
（1）image_records 已包含 title、notes、enabled、custom_metadata，但尚未单独建索引。
（2）document_records 已包含 document_type、tags、notes、enabled、custom_metadata、parse_backend、parse_stage、progress_percent、progress_message 等扩展字段。
（3）chat_messages 已包含 retrieval_steps_json，说明会话型 RAG 的数据追踪已进入现状实现。

因此，本系统数据库设计需要明确区分两层含义：
1）目标模型设计：以后端 ORM 定义为准，体现最终业务结构。
2）现状实现参考：以 backend/test_data/app_test.db 为准，体现当前开发阶段已落库的真实表结构。

6. 实体关系设计
（1）ChatSession 与 ChatMessage 为一对多关系。
（2）DocumentRecord 与文档图片资产之间为一对多逻辑关系，当前通过图片记录的 extra_metadata 或关联元数据进行映射。
（3）ImageRecord 与 Chroma 图片向量集合之间是一对一逻辑映射。
（4）DocumentRecord 与文档切块向量之间是一对多逻辑映射。
（5）聊天消息中的 sources_json 可回溯到 ImageRecord、DocumentRecord 或文档 chunk。

七、关键流程设计
1. 图片上传入库流程
（1）用户在图片知识库页面上传图片。
（2）后端保存原始文件并创建 ImageRecord，初始状态为 Processing。
（3）系统调用图像描述链生成结构化描述。
（4）更新 ImageRecord 的 generated_description 和 status。
（5）将描述文本写入 Chroma 图片集合。
（6）必要时增量更新 BM25 索引。
（7）前端刷新后展示图片及描述。

2. 文本到图像检索流程
（1）用户输入文本查询。
（2）后端调用统一检索器执行文本检索。
（3）检索器将查询转向量，并在图片集合或混合集合中检索。
（4）若启用重排序，则对候选集进行 rerank。
（5）后端将结果封装为 SearchResultItem，返回给前端。
（6）前端以网格卡片形式展示结果及相似度。

3. 图像到图像检索流程
（1）用户上传查询图片。
（2）后端先调用图像描述链生成查询描述。
（3）系统将描述作为文本查询送入统一检索流程。
（4）返回检索结果和查询描述。
（5）前端同时展示“模型生成的查询描述”和相关图片结果。

4. 文档上传解析流程
（1）用户上传 PDF。
（2）后端创建 DocumentRecord，设置初始状态和进度。
（3）后台任务开始解析 PDF 文本和视觉资产。
（4）切分文本片段并写入文档向量集合。
（5）对页面图像、表格截图等生成对应图片资产与元数据。
（6）更新 chunk_count、image_count、parse_stage 和 status。
（7）前端轮询查看进度，完成后展示文本片段和图片资产。

5. 会话化 RAG 问答流程
（1）用户在聊天页输入问题，可选附加图片。
（2）若未指定 session_id，系统自动创建新会话。
（3）系统读取最近若干轮会话历史。
（4）若有图片，先完成图片语义化；否则直接进入检索。
（5）RAG 链检索相关图片描述、文档片段或混合证据。
（6）系统结合检索结果与历史消息构建 Prompt，由大语言模型生成答案。
（7）后端将用户消息、助手消息、sources_json、retrieval_params_json、retrieval_steps_json 落库。
（8）前端展示答案、引用图片和检索轨迹。

九、非功能设计
1. 性能设计
（1）使用 ChromaDB 持久化图片和文档向量索引，满足本地部署与快速迭代需求。
（2）使用文本切块和近邻检索控制上下文长度，降低生成成本。
（3）通过候选集数量、rerank top_k、上下文压缩等参数控制响应效率。

2. 可扩展性设计
（1）图像描述模型、嵌入模型、生成模型均通过配置项注入，便于替换不同服务商。
（2）文档解析后端支持 local 与 MinerU 两类策略，便于后续扩展。
（3）Agentic RAG、query rewrite、context compression 等增强能力已通过配置项预留开关。

3. 可解释性设计
（1）聊天回答返回 sources，支持证据回溯。
（2）消息中保存 retrieval_steps_json，便于展示调度轨迹。
（3）检索结果和聊天引用均尽量保留 file_path、page_number、score 等元数据。

4. 可维护性设计
（1）采用分层架构，路由层、业务层、数据层和集成层职责明确。
（2）前后端接口通过 schema 和 types 约束，降低联调成本。
（3）数据库采用渐进式补列方式，兼容开发过程中的结构演进。

5. 安全与部署设计
（1）敏感配置通过环境变量注入，不在代码中硬编码 API Key。
（2）开发环境使用 SQLite 和本地文件存储，便于单机部署和调试。
（3）CORS 仅对本地前端开发端口开放。
（4）删除文档和图片时通过显式 confirm 和后端同步清理机制控制误操作风险。

十、技术选型说明
1. FastAPI
系统后端采用 FastAPI 构建 REST API。该框架适合快速定义接口、依赖注入和异步服务，便于组织知识库管理、检索和聊天接口。

2. SQLAlchemy + SQLite
关系数据采用 SQLAlchemy ORM 管理，当前开发环境数据库选用 SQLite，适合毕业设计原型系统快速开发、调试和单机部署。

3. ChromaDB
系统使用 Chroma 持久化向量集合，符合当前项目“小到中等规模知识库、本地持久化、快速实验”的需求，也便于将图片描述和文档片段分别组织到不同 collection 中。

4. LangChain
系统使用 LangChain 组织图像描述链、检索链和 RAG 链，降低模型调用、检索器封装和上下文构建的重复实现成本。

5. Vue3 + TypeScript + Vite
前端采用 Vue3 技术栈，适合快速构建上传、搜索、会话和可视化页面，并通过组件化方式复用图片卡片、上传区和会话列表。

十一、系统设计特点与创新点
1. 以“语义描述桥接”替代直接复杂跨模态对齐，降低工程实现难度。
2. 以统一文本检索链路同时支持文本到图像和图像到图像双路检索。
3. 将文档解析、视觉资产提取和图像知识库纳入统一知识服务框架。
4. 在聊天流程中保留会话历史、引用来源和检索轨迹，增强系统可解释性。
5. 同时具备在线服务能力和离线实验能力，适合毕业设计论文中的系统实现与实验评测双重场景。

十二、结论
综合当前项目资料和实现现状，本系统在设计上已经从最初的“图片语义描述 + 双路检索 + RAG 问答”核心主线，扩展为一个包含图片知识库、文档知识库、统一检索、会话化问答和离线评测的多模态知识服务原型。其设计重点在于通过多模态大模型生成结构化文本语义，实现对图像和文档视觉内容的统一组织，再借助向量检索与大语言模型完成知识增强问答。

如果从开发前视角审视，该系统设计是完整且可实施的：在架构上采用分层解耦，在存储上实现关系型数据、向量索引和文件资源协同，在功能上覆盖知识入库、双路检索、会话问答和实验评测，在工程上保留了配置化替换和渐进升级能力。因此，该设计能够为当前项目后续实现、测试、论文撰写和答辩展示提供稳定依据。
