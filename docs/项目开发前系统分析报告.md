# 项目开发前系统分析报告

## 1. 系统分析背景

本课题拟围绕“基于语义描述桥接的多模态 RAG 系统设计与实现”展开，目标是在项目正式开发前，对系统建设的业务背景、功能需求、数据组织方式和总体技术路线进行系统分析，为后续系统设计、编码实现、测试验证和论文撰写提供依据。

随着图像、图表、扫描件、PDF 文档等非结构化数据在教学、科研和工程场景中的大量积累，传统基于关键词匹配或纯文本知识库的检索方式已难以满足复杂知识服务需求。尤其在检索增强生成（RAG）场景下，如果系统只能处理文本知识，就无法充分利用图像和文档中的视觉语义信息，进而影响知识召回的完整性和生成回答的准确性。

现有多模态检索方案通常有两类路径：一类是构建统一跨模态向量空间，实现图文直接对齐；另一类是先将图像、版面或视觉元素转化为文本，再复用成熟的文本检索链路。综合技术复杂度、系统可解释性、开发成本和毕业设计项目的可实施性，本项目拟采用第二种路径，即“语义描述桥接”方案：利用多模态大模型将图像和文档中的视觉内容转化为结构化文本描述，再通过文本向量化、向量检索和 RAG 生成完成系统闭环。

因此，本系统分析报告需要站在项目尚未开发的时间点，对系统建设目标、业务模型、功能模型和数据模型进行预先定义。虽然本报告的内容会参考当前项目最终形成的模块边界和技术实现情况进行反推整理，但叙述上应保持“开发前分析”的逻辑顺序，即先有系统分析，后有系统设计与实现。

## 2. 系统建设目标与分析范围

### 2.1 建设目标

本项目拟建设一个面向多模态知识组织、检索与问答的综合性 RAG 系统，其总体目标如下：

1. 支持图片、PDF 文档等多模态知识资源的统一接入与管理。
2. 支持文本检索图片、图片检索图片等双路检索能力。
3. 支持基于检索结果的多模态 RAG 智能问答。
4. 支持知识库资源的基本治理，包括查看、筛选、编辑、删除和重处理。
5. 支持多轮会话和来源追踪，增强系统的交互完整性与结果可解释性。
6. 支持离线评测，为后续实验部分提供 Recall、MRR、mAP 等量化指标。

### 2.2 分析范围

结合课题目标和预期实现内容，本次系统分析的范围主要包括以下四个子系统：

1. 图片知识库子系统
2. 文档知识库子系统
3. 多模态检索与 RAG 问答子系统
4. 离线评测与实验分析子系统

其中，本报告重点展开系统业务模型、功能模型和数据模型，并对总体流程和技术可行性作出分析。

## 3. 系统业务模型

### 3.1 业务参与者

从系统建设目标出发，项目拟涉及以下主要业务参与者：

#### （1）普通用户

普通用户通过前端界面完成图片上传、文档上传、文本检索、图片检索和智能问答等操作，是系统的主要服务对象。

#### （2）知识库维护人员

维护人员负责对知识库中的图片和文档资源进行分类、筛选、标注和管理，并根据需要执行删除、重处理或重新解析等维护操作，以保障知识库内容质量。

#### （3）系统服务模块

系统内部包括图像描述生成、文档解析、文本向量化、向量检索、RAG 生成和会话管理等服务模块。这些模块虽然不是传统意义上的“人”，但在业务建模中承担着关键处理角色。

#### （4）实验评测人员

实验评测人员负责构建数据集、配置不同检索方案、运行离线评测脚本并分析实验指标，为课题方法有效性提供量化支撑。

### 3.2 核心业务对象

系统拟围绕以下核心业务对象展开：

1. **图片资源**  
   作为图像知识单元，包含原始图片文件、语义描述、标签、来源和管理状态等信息。

2. **文档资源**  
   以 PDF 为主，包含原始文档、解析结果、文本分块、页面图像及其他派生资源。

3. **检索请求**  
   包括文本到图像检索、图像到图像检索以及问答场景下的知识召回请求。

4. **问答会话**  
   用于表示用户与系统之间的多轮交互过程，记录问题、回答、来源和检索过程信息。

5. **向量索引对象**  
   由图片描述文本或文档分块文本生成，承担语义检索入口的角色。

6. **评测样本**  
   包括查询样本、相关结果标注和不同方法的评测结果。

### 3.3 业务关系

系统的核心业务关系可概括为“知识入库、语义加工、检索召回、生成回答、实验验证”的闭环。

1. 用户上传图片后，系统需先保存原始文件，再调用多模态大模型生成语义描述，并将其写入数据库和向量索引。
2. 用户上传 PDF 文档后，系统需完成文本抽取、图像抽取、文档分块和向量化处理，使文档内容能够进入统一检索流程。
3. 用户发起文本查询时，系统需将问题转换为文本向量并在索引库中执行召回。
4. 用户发起以图搜图时，系统需先把查询图片转为描述文本，再复用文本检索链路完成相似内容查找。
5. 用户发起 RAG 问答时，系统需根据问题类型选择检索路径，将召回结果作为上下文提供给生成模型输出回答。
6. 在实验阶段，评测人员需基于标准样本集对系统方案与基线方案进行离线对比，以验证方案有效性。

### 3.4 业务流程

#### （1）图片入库流程

用户上传图片后，系统拟执行如下流程：

`上传图片 -> 保存原始文件 -> 生成语义描述 -> 写入图片记录 -> 写入向量库 -> 更新索引 -> 返回处理结果`

#### （2）文档入库流程

用户上传 PDF 后，系统拟执行如下流程：

`上传文档 -> 创建文档记录 -> 后台解析 -> 抽取文本与视觉资产 -> 文本分块 -> 向量化写入 -> 返回进度与结果`

#### （3）双路检索流程

文本检索流程如下：

`输入文本查询 -> 文本向量化 -> 向量召回 -> 排序与封装 -> 返回结果`

图像检索流程如下：

`上传查询图片 -> 生成图片描述 -> 文本向量化 -> 向量召回 -> 返回相似结果`

#### （4）RAG 问答流程

多模态 RAG 问答拟执行如下流程：

`输入问题（可附图） -> 读取会话上下文 -> 发起知识召回 -> 组织提示词 -> 调用大模型生成回答 -> 返回答案与来源`

从业务层面看，本系统并非单一的图像检索工具，而是一个围绕多模态知识资源管理、语义桥接检索和智能问答构建的知识服务平台。

## 4. 系统功能模型

### 4.1 总体功能结构

根据项目目标，系统拟划分为以下五个一级功能模块：

1. 图片知识库管理模块
2. 文档知识库管理模块
3. 双路检索模块
4. 会话化 RAG 问答模块
5. 离线评测与实验分析模块

### 4.2 图片知识库管理模块

该模块负责图片知识资源的接入、存储和治理，拟支持以下功能：

1. **图片上传**  
   支持单张或多张图片上传，并在上传后自动触发语义描述生成。

2. **图片列表查看**  
   支持按时间、状态、关键词、标签和来源进行筛选。

3. **图片详情查看**  
   支持查看图片元数据、描述内容和处理状态。

4. **图片信息维护**  
   支持编辑标题、标签、备注、自定义元数据和启停状态。

5. **图片删除与重处理**  
   支持删除失效资源，并允许在模型策略调整后重新生成描述和索引。

### 4.3 文档知识库管理模块

考虑到实际知识资源常以 PDF、报告和图文资料形式存在，系统拟增加文档知识库功能，以增强知识覆盖能力。该模块拟支持：

1. **PDF 上传**
2. **后台解析与进度跟踪**
3. **文档列表与详情查看**
4. **解析结果查看**
5. **文档标签、备注和启停维护**
6. **文档删除与重新解析**

通过该模块，系统可将原本难以直接参与问答的复合文档资源转化为可检索知识单元。

### 4.4 双路检索模块

双路检索模块是系统的核心功能模块之一，拟支持以下能力：

1. **文本到图像检索**  
   用户输入自然语言描述，系统返回语义相关的图片结果。

2. **图像到图像检索**  
   用户上传查询图片，系统先生成其语义描述，再执行相似图片搜索。

3. **结果排序与打分**  
   系统需对检索结果提供相似度分数，并根据业务需求进行排序。

4. **结果元数据展示**  
   检索结果需返回文件路径、描述摘要、分页信息或其他辅助字段，用于前端展示和后续问答引用。

该模块的本质是将不同模态输入统一转换到文本语义空间内进行检索，从而降低多模态检索的实现复杂度。

### 4.5 会话化 RAG 问答模块

系统拟在检索模块基础上构建问答能力，使用户能够直接以自然语言获取知识服务。该模块拟支持：

1. **新建会话**
2. **查看会话列表**
3. **查看消息历史**
4. **重命名或删除会话**
5. **普通文本问答**
6. **带图问答**
7. **流式响应**
8. **来源追踪与检索步骤记录**

该模块可将知识检索与答案生成结合起来，使系统从“返回结果”升级为“提供解释性回答”。

### 4.6 离线评测与实验分析模块

为了验证所提方案的有效性，系统拟设计独立的离线评测模块，主要功能包括：

1. 加载评测数据集
2. 构建不同检索方案
3. 运行 Recall@K、MRR、mAP 等评测指标
4. 对比 Proposed 方法与基线方法
5. 输出实验结果供论文分析使用

该模块虽然不直接面向普通用户，但对毕业设计课题的研究价值验证具有重要意义。

## 5. 系统数据模型

### 5.1 数据架构总体思路

本项目拟采用“关系数据库 + 文件存储 + 向量数据库”相结合的数据架构。

1. **关系数据库**  
   用于保存业务主数据，如图片记录、文档记录、聊天会话和消息记录。

2. **文件存储**  
   用于保存原始图片、PDF 文档和解析过程中产生的派生文件。

3. **向量数据库**  
   用于保存语义描述文本或文档分块文本对应的向量索引，以支持语义检索。

这一组合方式既能保证业务数据管理的稳定性，也能满足多模态语义检索的性能需求。

### 5.2 图片数据模型

图片资源是系统中的基础实体，开发前分析中可抽象为 `ImageRecord`。其主要字段拟包括：

| 字段名 | 类型 | 说明 |
|---|---|---|
| id | UUID/String | 图片唯一标识 |
| file_path | String | 图片存储路径 |
| upload_time | DateTime | 上传时间 |
| generated_description | Text | 由多模态模型生成的语义描述 |
| status | String | 处理状态 |
| source_dataset | String | 来源数据集 |
| title | String | 图片标题 |
| tags | String/List | 标签信息 |
| notes | Text | 备注 |
| enabled | Boolean | 是否参与检索 |
| custom_metadata | JSON/Text | 扩展元数据 |

该模型用于统一管理图片文件、语义描述和治理信息。

### 5.3 文档数据模型

文档资源可抽象为 `DocumentRecord`，主要字段拟包括：

| 字段名 | 类型 | 说明 |
|---|---|---|
| id | UUID/String | 文档唯一标识 |
| file_name | String | 原始文件名 |
| title | String | 展示标题 |
| file_path | String | 文档存储路径 |
| upload_time | DateTime | 上传时间 |
| status | String | 处理状态 |
| chunk_count | Integer | 文本分块数量 |
| image_count | Integer | 抽取图片数量 |
| document_type | String | 文档类型 |
| tags | String/List | 标签 |
| notes | Text | 备注 |
| enabled | Boolean | 是否启用 |
| parse_backend | String | 解析方式 |
| parse_stage | String | 当前解析阶段 |
| progress_percent | Integer | 解析进度 |
| progress_message | Text | 进度说明 |

该模型体现文档知识库并非简单文件上传，而是一个需要解析、分块和持续跟踪处理状态的知识加工过程。

### 5.4 会话数据模型

为支持多轮问答，系统拟采用“会话 + 消息”二级模型。

#### （1）ChatSession

用于表示一个独立对话上下文，主要字段包括：

| 字段名 | 类型 | 说明 |
|---|---|---|
| id | UUID/String | 会话标识 |
| title | String | 会话标题 |
| created_at | DateTime | 创建时间 |
| updated_at | DateTime | 更新时间 |

#### （2）ChatMessage

用于记录单条消息及其检索上下文，主要字段包括：

| 字段名 | 类型 | 说明 |
|---|---|---|
| id | Integer | 消息主键 |
| session_id | String | 所属会话 ID |
| role | String | user/assistant |
| content | Text | 消息内容 |
| has_image | Boolean | 是否包含图片 |
| sources_json | Text/JSON | 引用来源 |
| retrieval_params_json | Text/JSON | 检索参数 |
| retrieval_steps_json | Text/JSON | 检索过程记录 |
| created_at | DateTime | 创建时间 |

该设计有利于保存完整问答链路，并提升系统结果的可追溯性。

### 5.5 向量索引模型

向量数据库中虽然不一定以传统关系表形式存在，但在系统分析中仍可抽象出逻辑数据模型。其主要字段包括：

| 字段名 | 类型 | 说明 |
|---|---|---|
| doc_id | String | 与图片或文档块关联的唯一标识 |
| text | Text | 用于向量化的文本内容 |
| embedding | Vector | 文本对应向量 |
| metadata | JSON | 文件路径、标题、页码、状态等扩展信息 |

该模型实现了知识对象与检索索引对象之间的连接，是整个系统语义检索能力的基础。

### 5.6 数据关联关系

从开发前角度看，系统中主要存在以下关联关系：

1. 一条图片记录对应一个图片文件和一个向量索引对象。
2. 一条文档记录对应一个原始 PDF 文件，并可派生出多个文本块和多个图片资源。
3. 一条会话记录对应多条消息记录。
4. 一条消息记录可关联多个来源项。
5. 评测数据中的相关标注需与系统资源 ID 保持一致，以便进行离线指标计算。

因此，系统开发前必须重点考虑多存储之间的主键一致性、删除同步和索引重建机制。

## 6. 系统总体流程与技术路线分析

### 6.1 总体流程

根据系统目标，可将总体处理流程概括为：

`资源接入 -> 语义加工 -> 向量化索引 -> 检索召回 -> RAG 生成 -> 会话记录 -> 离线评测`

这一流程说明系统既面向在线业务，也面向研究验证。

### 6.2 技术路线

项目拟采用如下技术路线：

1. 使用 FastAPI 构建后端服务接口；
2. 使用 Vue3 + TypeScript + Vite 构建前端交互界面；
3. 使用 SQLite 存储结构化业务数据；
4. 使用文件系统保存原始资源文件；
5. 使用 ChromaDB 构建语义向量索引；
6. 使用多模态大模型完成图像语义描述生成；
7. 使用文本 Embedding 模型完成语义向量化；
8. 使用大语言模型完成检索增强生成回答；
9. 使用离线评测脚本完成实验验证。

### 6.3 关键设计思想

本项目在开发前分析中应明确以下关键设计思想：

1. **描述桥接优先于复杂跨模态对齐**  
   优先通过多模态模型把视觉内容转成文本，再复用成熟文本检索链路。

2. **知识库管理与问答服务并重**  
   系统不仅要“能问答”，也要“能管理知识资源”。

3. **会话化与可解释性并重**  
   问答结果应尽量保留来源信息和检索步骤。

4. **实验验证与系统实现并重**  
   毕业设计项目需要通过实验数据证明方法有效，而不仅是完成功能演示。

## 7. 系统可行性分析

### 7.1 技术可行性

项目拟采用的技术栈成熟度较高，具备较强可实施性：

1. FastAPI 适合快速构建异步接口服务；
2. Vue3 适合搭建交互式前端页面；
3. SQLite 适合中小规模毕业设计项目的数据管理；
4. ChromaDB 易于集成，适合作为向量检索原型库；
5. 多模态大模型已具备较强图像理解与描述能力；
6. LangChain 或类似框架适合封装检索与 RAG 编排逻辑。

因此，从技术层面看，系统建设具备现实基础。

### 7.2 业务可行性

多模态知识检索与智能问答在教育、科研、工业知识库、技术文档管理等场景中具有明确应用需求。尤其是在大量知识以图片、图表、PDF 文档形式存在的场景下，传统文本型知识库难以覆盖实际需要，因此本项目具有较强业务合理性。

### 7.3 实验可行性

通过构建标准化评测数据集、设计基线方法和设置统一指标，本项目可以对系统方案进行定量验证，满足毕业设计对于实验分析部分的要求，因而具备较好的研究可行性。

## 8. 系统分析结论

在项目正式开发前，可以将本系统定义为一个面向多模态知识管理、双路语义检索和检索增强问答的综合平台。系统的核心创新点在于通过多模态大模型生成语义描述，将原本复杂的跨模态检索问题转换为相对成熟的文本检索问题，从而在保证系统可解释性和开发可行性的同时，提高图像和文档知识接入 RAG 流程的能力。

从业务层面看，系统将形成“资源入库、语义加工、语义检索、智能问答、实验验证”的完整闭环；从功能层面看，系统需覆盖图片管理、文档管理、双路检索、会话问答和离线评测等核心模块；从数据层面看，系统需采用关系数据库、文件存储和向量数据库协同的数据组织方式，以满足多模态知识服务的实际需要。

综上所述，本项目具备明确的问题背景、合理的建设目标、可拆解的功能结构、清晰的数据模型和可落地的技术路线，具备开展系统设计与实现工作的前提条件。后续开发阶段应在本系统分析的基础上进一步完成总体架构设计、模块设计、数据库设计、接口设计和测试方案设计。
