以下记录结合开题报告、中期报告、系统设计报告、README，以及当前项目代码与工程实现整理，时间均选自 `2026-01-15 ~ 2026-02-10` 和 `2026-02-20 ~ 2026-04-08` 两个区间。内容按项目实际推进节奏编写，覆盖技术调研、系统分析、工程实现、联调与实验评测等阶段。

## 1. 第一次记录

**每周工作记事**  
本周主要围绕开题后的技术路线调研展开，重点阅读了多模态检索、多模态 RAG、向量数据库和视觉语言模型相关资料，并对比了“直接做图文统一向量空间检索”和“先用多模态模型生成图像描述，再走文本检索链路”两种方案。同时开始梳理系统原型的最小闭环，计划先实现图片知识库、文本检索、以图搜图和基础问答，再考虑后续扩展。

**问题简述**  
当前最大的疑问是论文主线到底应该强调“跨模态检索能力”还是“语义描述桥接能力”。如果一开始就采用 CLIP 一类统一向量空间方案，理论上更符合传统多模态检索，但工程复杂度较高，也不容易解释为什么结果命中；如果采用“图像先转结构化文本描述”的方案，更容易接入成熟文本 RAG，但担心论文创新点会显得不足，且描述质量一旦不稳定，会直接影响后续检索和问答。

**教师回答**  
课题重点不在于追求最复杂的跨模态建模，而在于提出一条适合本科毕设周期、可实现、可验证、可解释的技术路线。你可以把“语义描述桥接”作为核心思路，把复杂的多模态问题转成较成熟的文本检索问题，这本身就是方案取舍。论文中需要把两条路线的优缺点讲清楚，并通过实验说明你的方法在工程可落地性和解释性上更有优势，不必一开始就把目标设成统一跨模态向量空间。

## 2. 第二次记录

**每周工作记事**  
本周继续细化图像语义化方案，参考了项目后续准备用到的多模态模型接口形态，开始设计图像描述提示词，希望生成的结果不仅包含对象名称，还能覆盖颜色、空间关系、场景语义等信息。同时初步思考后端服务形态，计划使用 FastAPI 暴露上传、检索和问答接口，避免后续功能扩展时接口风格混乱。

**问题简述**  
我在调研中发现，如果图像描述只是简单标签堆叠，后续 embedding 检索效果可能很一般；但如果描述写得过长，又会带来冗余信息，甚至使不同图像描述模板不一致。这个问题会直接影响以后代码里图像上传后生成 `generated_description` 再写入向量库的质量。想请教描述生成阶段到底应该追求“丰富”还是“稳定”，论文里是否需要单独交代描述质量控制策略。

**教师回答**  
描述生成不要走“越长越好”的思路，而要追求可检索性和一致性。建议你在提示词里约束输出结构，至少覆盖主体、属性、空间关系和场景语义四个方面，并控制长度，使不同样本的描述风格尽量一致。论文中可以把这部分写成“模板约束与提示工程的描述质量控制”，哪怕你后面只做人工抽样分析，也比完全放任模型自由生成更有说服力。

## 3. 第三次记录

**每周工作记事**  
本周开始同步梳理系统评测思路，计划以 MS-COCO 子集作为初始实验数据基础，为后续 `evaluation` 目录下的离线脚本做准备。除了 proposed 方法，还在调研可作为基线的方法，包括基于跨模态 embedding 的图文检索路线，以及 OCR/文本抽取后的文本检索路线。

**问题简述**  
目前比较担心的是，后续实验如果只展示系统能跑通，而没有规范的 baseline，对论文支撑会比较弱。但多种方法的索引构建方式不同，例如描述桥接法会写入描述文本向量，跨模态 embedding 方法可能直接写图像向量，OCR 路线又涉及文本抽取质量，容易导致实验比较不公平。想确认在毕设阶段应该把实验重点放在“绝对性能最优”，还是“在同一数据集和同一任务定义下做可解释的对比”。

**教师回答**  
本科毕设实验最重要的是可复现和可比性，不必追求覆盖所有最强方法。你可以先明确任务定义，再让各方法在尽量一致的数据集和标注规则下比较，尤其要保证 `relevant_ids`、检索集合和评测指标口径统一。后续如果代码里实现了 `Recall@K`、`MRR`、`mAP` 这些指标，就足够支撑论文实验分析，关键是说明每个 baseline 的输入、索引和检索流程。

**问题简述**  
随着调研深入，我发现如果后期再把文档知识库、会话管理、结果可解释性、实验模块全部堆进来，工作量可能会迅速超出开题预期。尤其从工程角度看，图片文件、数据库记录和向量库索引之间还要保持映射一致，后期一旦出现删除、重处理、增量更新，系统复杂度会上升。想请教目前是否应该先把题目范围控制在“图像知识库 + 双路检索 + RAG 问答”的主线，再预留扩展能力。

**教师回答**  
范围一定要控制。先把图像知识库、文本到图像检索、图像到图像检索和基于检索的问答闭环打通，这是你论文的核心。其余内容例如文档知识库、会话持久化、解释性展示可以作为增强模块，但不能反过来冲淡主线。实现时要尽量做好模块解耦，让后续扩展是在现有接口和存储体系上叠加，而不是推翻重做。

**问题简述**

**教师回答**  
这是正常的工程抽象，不会偏离论文。你的论文要体现“模块化设计”，代码里把路由层保持轻量，把实际编排逻辑下沉到适配层或服务层，反而更能说明系统结构清晰。写作时可以说路由层负责参数接收与响应封装，应用层负责入库编排、双路检索调度和问答流程控制，这与后续你在代码中采用的分层方式是一致的。

**每周工作记事**  
本周开始聚焦知识库主链路，梳理图片上传后的一致性问题。结合后续后端实现，已经明确每张图片需要有唯一 ID，对应文件路径、数据库记录和向量索引，同时还要考虑启用状态、标签、来源数据集等管理字段，便于前端知识库页面进行筛选和维护。

**问题简述**  
随着功能细化，我发现图片知识库并不是“上传完成就结束”那么简单。后续代码中 `kb.py` 里已经包含列表、详情、编辑、删除和重处理接口，而 `knowledge_management.py` 也需要负责字段补全和安全删除。如果图片删除了但向量库中还保留旧索引，或者更新标题/标签后检索索引不同步，就会出现结果和管理界面不一致的问题。想请教论文里是否需要突出这种“三存储一致性”问题，以及工程上应如何界定重点。

**教师回答**  
这个问题很值得写，因为它体现了系统从“演示脚本”到“可管理知识库”的区别。你可以把图片原文件、关系型数据库和向量库的一致性视为系统实现中的一个关键工程问题。论文里不需要展开到很底层，但应说明每条图像数据都通过统一 ID 关联，删除、重处理和属性更新要同步影响数据库记录和检索索引，这样你的知识库管理模块才是完整的。

## 7. 第七次记录

**每周工作记事**  
本周重点推进双路检索原型，已经明确后端会通过 `/api/search/text-to-image` 和 `/api/search/image-to-image` 两条接口承载两类查询，前端 `Search.vue` 也计划分别提供文本输入和图片上传入口。其中以图搜图并不直接做图像特征匹配，而是先由模型生成查询图像描述，再复用文本检索链路。

**问题简述**  
从代码设计上看，搜索模块中两条搜索接口最终都要返回统一的 `SearchResultItem`，这有利于前端复用结果卡片和预览组件。但我担心在论文表达上，如果两条路径都落到“文本检索”，会让人误以为图像到图像检索只是换了个输入形式，缺少技术含量。另一方面，如果强行把它写成完全不同的技术链路，又和当前工程实现不一致。想请教该如何准确表述“双路检索”的意义。

**教师回答**  
双路检索的关键不在于底层用了两套完全不同的检索器，而在于系统支持两种不同用户输入形态，并通过统一语义中间层完成检索调度。你完全可以在论文中强调：文本查询直接进入文本检索通路，图像查询先经过语义化层转成结构化描述，再进入同一检索通路，这种设计既降低了工程复杂度，又保证了系统接口统一和结果可解释性。

**每周工作记事**  
本周开始联通问答模块与检索模块，围绕 `/api/rag/chat` 和 `/api/rag/chat/stream` 两类接口设计前后端交互。除了返回回答文本，还希望把检索结果、引用来源和过程信息一并返回，以便前端聊天页面显示来源图片和检索轨迹。与此同时，会话相关的创建、列表、重命名和删除接口也进入实现规划。

**问题简述**  
在实际工程实现中，我发现如果问答接口只返回一句答案，演示虽然简单，但论文很难体现“RAG 确实调用了知识库”；而如果把检索来源、相似度、模式判断、历史消息等都暴露出来，接口结构又会变复杂。当前 `chat.py` 里的思路是除了 `answer` 外，还保留 `sources`、`results`、`session_id`、`retrieval_steps` 等字段，同时前端 `Chat.vue` 也会展示引用图片和轨迹。想确认这种“偏工程化”的可解释性设计，是否值得在论文中占一定篇幅。

**教师回答**  
值得写，但要把握层次。论文主线仍然是基于检索增强生成的多模态问答，你可以把来源图片、引用信息和检索轨迹作为“提升可解释性与可用性”的增强设计来写。这样既能说明系统不是黑箱生成，也能解释为什么你在前端展示引用图片、在后端保存来源快照和检索参数。不要把这些细节写成接口文档，而是提炼成“来源回溯”和“过程可视化”两个设计点。

**问题简述**  
从研究目标看，会话管理并不是开题报告里最早期的核心内容，但在真实使用中，如果聊天页面每问一次都丢失上下文，就很难体现 RAG 系统的连续交互能力。当前 `chat.py` 和 `chat_service.py` 的设计已经把最近若干轮历史消息作为上下文的一部分，同时保存 `retrieval_steps` 和 `sources_json`。我担心这部分如果完全不写，会低估系统完整性；写得过多，又会让人觉得重点从检索和问答偏向了通用聊天系统。

**教师回答**  
这部分要“写，但控制篇幅”。会话管理不是论文创新点，但它是系统可用性的关键支撑。你可以把它归到“会话与历史管理模块”，说明系统支持连续问答、消息持久化和来源保留，从而为多轮 RAG 提供上下文基础。不要把数据库表字段和前端交互细节展开太多，重点写它如何服务于检索增强问答，而不是单纯做一个聊天壳子。
