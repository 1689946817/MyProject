# 开发技术调研报告

## 1. 调研背景

本课题拟开发一个基于多模态大模型与双路检索的多模态 RAG 知识库系统，面向图像、图表、页面截图以及后续可扩展的多模态文档场景，支持以下核心能力：

- 图片知识库构建
- 文本到图像检索
- 图像到图像检索
- 基于检索增强的多模态问答
- 可视化交互与实验评测

传统 RAG 系统主要处理纯文本知识，难以直接利用图像、图表和页面结构中包含的语义信息；而直接采用跨模态统一向量空间进行检索，虽然链路较短，但在垂直领域、复杂图表和专业文档场景中，对模型能力、数据质量和对齐效果依赖较强，系统可解释性也相对不足。因此，在正式开发前，有必要围绕 RAG 系统、向量数据库、多模态大模型、嵌入模型和系统工程架构进行系统调研，形成可执行的技术选型结论。

## 2. 调研目标

本次调研的目标主要包括以下几个方面：

1. 明确多模态 RAG 系统的主流技术路线及其适用场景。
2. 对比“直接跨模态检索”与“图像语义描述桥接检索”两类方案的优缺点。
3. 评估向量数据库、元数据管理与文件存储的组合方式。
4. 选择适合本课题实现周期和硬件条件的后端、前端与模型调用方案。
5. 为后续系统设计、实现与实验评估提供依据。

## 3. 多模态 RAG 技术调研

### 3.1 RAG 基本原理

RAG（Retrieval-Augmented Generation）是指在生成模型回答问题之前，先从外部知识库中检索相关内容，并将其作为上下文输入给大模型，从而提升回答的事实性、准确性和可追溯性。传统 RAG 的知识对象通常是文本块，因此可以依赖文本切分、文本 embedding 和向量检索构建标准流程。

随着多模态大模型的发展，RAG 的知识源逐渐从纯文本扩展到图像、图表、音频、视频和多模态文档。多模态 RAG 的核心问题不再只是“如何召回文本”，而是“如何统一组织和检索不同模态的信息，并有效地送入生成模型”。相关综述指出，多模态 RAG 的难点主要体现在以下方面：

- 不同模态之间的语义对齐难度高
- 检索结果的表示形式不统一
- 多模态上下文拼接复杂
- 引用与证据返回机制较难设计
- 评估指标与实验范式尚未完全统一

### 3.2 多模态 RAG 的两类主流方案

#### 方案一：直接跨模态统一向量空间

该方案通常基于 CLIP 或多模态 embedding 模型，将文本和图像编码到同一向量空间中，再完成文本到图像或图像到图像检索。其优点是：

- 技术链路较短
- 适合实现统一检索接口
- 在自然图像、视觉相似检索场景下效果较好

其缺点主要包括：

- 依赖统一跨模态表征质量
- 对专业场景、抽象语义和复杂图表适应性不一定稳定
- 检索命中的语义原因不易解释
- 当后续要加入 BM25、过滤器、文本引用和问答上下文控制时，扩展成本较高

#### 方案二：语义描述桥接方案

该方案先使用多模态大模型对图像生成高质量结构化文本描述，再将图像检索问题转化为文本检索问题。其优点包括：

- 可以复用成熟的文本 embedding 与文本检索技术
- 更容易加入关键词检索、重排序和 metadata filter
- 检索结果更易解释，适合论文论证和答辩展示
- 对图表、截图、页面结构等“视觉上复杂、语义上强”的对象更友好

其缺点包括：

- 额外引入图像描述生成步骤，增加调用成本和时延
- 描述质量会直接影响检索效果
- 对提示词设计和描述模板依赖较大

综合考虑本课题的研究目标、工程实现难度、可解释性要求和开发周期，语义描述桥接方案更适合作为主系统路线。

### 3.3 多模态 RAG 的系统演进方向

除基础检索外，当前 RAG 系统的优化重点主要包括：

- Query Rewrite / Multi-Query：提升模糊查询和复杂查询的召回率
- Hybrid Retrieval：结合向量检索与关键词检索
- Re-ranking：使用 CrossEncoder 或 reranker 提高最终排序质量
- Context Compression：压缩无关上下文，减少噪声
- Citation / Evidence：返回可引用来源，增强系统可信度
- Session Memory：支持会话化问答与多轮交互

因此，在开发阶段，系统不宜停留在“向量库 + LLM”的简单组合上，而应预留上述能力的扩展空间。

## 4. 向量数据库与存储架构调研

### 4.1 向量数据库的作用

在本课题中，向量数据库主要承担以下职责：

- 存储图像描述文本的向量
- 存储后续文档文本块的向量
- 支持相似度检索
- 支持按 metadata 进行过滤
- 支持按集合管理不同类型或不同实验用途的数据

因此，向量数据库不仅要具备检索能力，还应具备较好的本地部署能力和开发友好性。

### 4.2 主流方案对比

#### Milvus

Milvus 是面向大规模向量检索的专业向量数据库，支持 IVF、HNSW 等索引结构，适合大规模数据和分布式部署。优点是性能强、生态成熟，缺点是部署和维护成本较高，对本科毕设型项目而言偏重。

#### Qdrant / Weaviate

这类产品在 metadata、过滤和服务化部署方面较完善，也适合中大型系统。但对于单机实验、快速原型开发而言，环境配置与运维复杂度仍高于轻量方案。

#### Chroma

Chroma 是面向 AI 应用开发的轻量级向量数据库，支持本地持久化、集合管理、metadata 过滤，并可与 LangChain 直接集成。其优点包括：

- 本地部署简单，适合快速搭建原型
- 可通过 `persist_directory` 直接落盘
- 支持 collection 级管理
- 支持 metadata filter
- 与 LangChain 集成成本低

其局限包括：

- 更适合中小规模、本地或单机使用
- 对超大规模数据、高并发和复杂运维支持不如 Milvus
- 全文检索能力弱，需要配合 BM25 等模块补充

### 4.3 本课题的存储架构建议

综合调研结果，建议采用“三存储协同”的架构：

- 关系型数据库：存储图像、文档、会话、消息、状态等结构化元数据
- 向量数据库：存储图像描述向量与文本块向量
- 文件存储：保存原始图片、文档和派生资源

关系型数据库方面，SQLite 足以满足毕设阶段的单机开发和演示需求；向量库方面，Chroma 更符合快速实现与本地复现需求；原始文件则可统一放在本地目录中管理，并通过唯一 ID 维持数据库记录、向量条目和文件资源的一致性。

因此，建议本课题采用：

- SQLite 作为结构化元数据存储
- Chroma 作为本地向量数据库
- 本地文件系统作为图片和文档资源存储

## 5. 多模态大模型与嵌入模型调研

### 5.1 多模态大模型的任务定位

在本课题中，多模态大模型不应仅作为“最后回答问题的生成器”，还应承担前置语义建模职责，即：

- 对上传图像生成结构化描述
- 对查询图像生成检索用描述
- 在问答阶段理解图片与检索结果，生成最终回答

因此，模型需要同时具备：

- 图像理解能力
- 图像描述生成能力
- 多模态问答能力
- 稳定的 API 调用方式

### 5.2 主流模型调研

#### BLIP-2

BLIP-2 通过轻量的 Q-Former 连接视觉编码器与语言模型，具有较强的视觉语言理解能力，是多模态建模中的代表性工作。其研究意义较强，但从工程上看，自行部署和调优成本相对较高。

#### LLaVA

LLaVA 在视觉指令调优方面表现突出，适合视觉问答、图像理解和多模态对话。其开源生态较强，适合作为研究参考或本地化替代方案。

#### Qwen-VL / Qwen 系列视觉理解模型

Qwen-VL 及后续视觉理解模型在中文场景、文档理解、视觉问答和 API 可用性方面具有明显优势。阿里云 Model Studio 文档表明，此类模型可以通过 OpenAI 兼容接口或原生接口完成图像理解和多模态对话，这对于系统开发非常有利。

综合考虑中文支持、接口稳定性、调用便利性和后续文档场景扩展需求，Qwen-VL 或同类阿里云视觉理解模型更适合作为本课题的首选多模态模型路线。

### 5.3 图像描述生成策略调研

为了让图像描述既能服务检索，又能服务问答，不适合只输出一句简单 caption，而应采用结构化描述模板。描述内容建议覆盖以下信息：

- 图像类型判断
- 语义摘要
- 关键视觉元素
- 空间关系与属性特征
- 图中文字信息
- 检索关键词

这种“结构化描述 + 检索关键词”的输出形式有三个好处：

- 提高文本检索召回率
- 增强图像内容的可解释性
- 便于后续问答时构造更稳定的上下文

### 5.4 文本 embedding 模型调研

在描述桥接方案中，文本 embedding 模型决定了图像描述、文本查询和文档块之间的语义匹配能力。应重点考虑以下因素：

- 中文效果
- 多语言兼容性
- 检索场景适配性
- API 或本地推理便利性

#### BGE 系列

BGE（BAAI General Embedding）是当前较成熟的文本 embedding 系列，BGE-M3 进一步强调多语言、多功能和多粒度能力，适合检索任务。其生态中还包括 bge-reranker 等配套模型，可用于精排。

#### text-embedding-v4

阿里云 Model Studio 提供的 `text-embedding-v4` 支持多维度设置，可用于检索、聚类和分类任务，并支持 `query` 与 `document` 角色区分，适合作为云端 embedding 方案。

综合考虑工程便利性与兼容性，开发阶段可优先采用云端文本 embedding 模型快速实现检索主流程，同时保留使用 BGE 系列本地模型进行 rerank 或后续替换的空间。

### 5.5 多模态 embedding 模型调研

`qwen3-vl-embedding` 等多模态 embedding 模型可以直接完成文本、图像、视频的统一向量表达，适合 text-to-image 或 image-to-image 的直接检索。该类模型适合用作以下用途：

- 构建 baseline，对比主方案效果
- 处理自然图像为主的跨模态检索任务
- 用于补充视觉相似检索能力

但作为主系统路线，其缺点在于：

- 对统一向量空间质量依赖较强
- 后续接入 BM25、文本引用、结构化过滤时不够自然
- 对复杂图表、页面布局和垂直场景的解释性偏弱

因此，本课题更适合将多模态 embedding 方案作为对照实验，而不是主路线。

## 6. 后端、前端与系统工程技术调研

### 6.1 后端框架选型

后端需要支持图片上传、文档上传、检索接口、问答接口、会话接口以及实验管理接口。FastAPI 具有以下优势：

- 异步支持较好，适合模型调用和文件处理
- 与 Pydantic、SQLAlchemy 配合自然
- 开发效率高，文档生成方便
- 适合构建研究型原型系统

因此，建议采用 Python 3.10+ 与 FastAPI 构建后端。

### 6.2 前端框架选型

前端需要支持：

- 知识库上传与管理
- 检索输入与结果展示
- 图片网格与详情预览
- 多轮聊天界面
- 引用来源与证据展示

Vue 3 + TypeScript + Vite 在开发效率、组件化和工程组织方面较适合本课题；若配合 Element Plus，可快速完成管理端和交互页面开发。因此，建议采用 Vue 3 + TypeScript + Vite 作为前端技术栈。

### 6.3 系统架构建议

建议采用五层架构组织系统：

1. 数据层：文件存储、关系数据库、向量数据库
2. 语义化层：图像描述生成、描述质量控制
3. 检索层：文本 embedding、向量检索、BM25、重排序
4. 应用层：双路检索调度、RAG 编排、会话管理
5. 展示层：前端页面、交互组件与可视化结果

这种分层结构既符合论文表达，也有利于后续模块解耦和演进。

## 7. 开发前技术选型结论

基于本次调研，建议本课题在正式开发时采用以下总体方案。

### 7.1 主路线

以“多模态大模型生成图像结构化描述，再通过文本检索完成召回”的语义描述桥接方案作为主路线，支持：

- 文本到图像检索
- 图像到图像检索
- 检索增强问答

### 7.2 核心技术选型

- 后端框架：FastAPI
- 前端框架：Vue 3 + TypeScript + Vite
- 关系型数据库：SQLite
- 向量数据库：Chroma
- 多模态模型：Qwen-VL 或同类视觉理解模型
- 文本 embedding：BGE 系列或 text-embedding-v4
- 重排序模型：BGE Reranker 等 CrossEncoder

### 7.3 检索链路建议

主检索链路建议按以下顺序设计：

1. 图像入库时生成结构化描述
2. 描述文本向量化并写入向量库
3. 文本查询直接向量检索
4. 图像查询先生成描述，再复用文本检索链路
5. 在基础检索之上逐步加入：
   - Query Rewrite
   - BM25 + 向量混合检索
   - Re-ranking
   - Metadata Filter

### 7.4 问答链路建议

问答时不应只把检索文本片段送入 LLM，而应根据需要联合使用：

- 检索到的图像描述
- 原始图片或缩略图
- 文档文本块
- 用户当前问题
- 历史上下文

最终形成多模态 Prompt，以提高问答质量与可信度。

### 7.5 实验评测建议

为了保证本课题具有研究性，建议开发初期就同步规划实验评测。评测应包含两部分：

- 检索评测：Recall@K、MRR、mAP
- 生成评测：回答正确性、相关性、图文一致性

同时应设置以下基线：

- 直接多模态 embedding 检索 baseline
- OCR 文本检索 baseline
- 无 RAG baseline

这样既能体现主方案的效果，也便于在论文中进行充分对比。

## 8. 预期风险与应对策略

### 风险一：图像描述质量不稳定

如果描述过短、过泛或不一致，会直接影响检索质量。

应对策略：

- 使用固定模板和提示词约束
- 增加描述质量检查
- 对关键样本进行人工抽样校验

### 风险二：仅靠向量检索可能漏召

纯向量检索对精确术语、图中文字和专业短语的召回能力有限。

应对策略：

- 引入 BM25
- 使用混合检索
- 对结果进行重排序

### 风险三：系统模块耦合过高

如果上传、描述生成、向量入库、问答逻辑混杂在一起，会影响后期维护。

应对策略：

- 使用清晰的分层架构
- 通过统一适配层封装业务入口
- 将模型、检索、数据存储职责分离

### 风险四：实验结果难以解释

若只给出定量指标而缺少对比逻辑和来源说明，论文说服力不足。

应对策略：

- 设计清晰 baseline
- 保存检索来源和引用证据
- 结合案例分析展示系统行为

## 9. 总结

经过对多模态 RAG、向量数据库、多模态大模型、嵌入模型及系统工程方案的调研，可以得出结论：本课题最适合采用“语义描述桥接”的多模态 RAG 路线，即利用多模态大模型将图像转化为高质量结构化文本描述，再复用成熟的文本检索与 RAG 技术体系构建系统。该方案兼顾可实现性、可解释性、扩展性和论文研究价值，适合作为本课题的核心开发路线。

在具体工程实现上，建议采用 FastAPI + Vue3 + SQLite + Chroma 的轻量组合，使用多模态大模型完成图像理解与多模态问答，使用文本 embedding 完成统一检索，并预留混合检索、重排序、会话管理和引用返回等能力。该技术路线既符合当前多模态 RAG 的发展方向，也适合在本科毕业设计周期内完成系统原型开发与实验验证。
